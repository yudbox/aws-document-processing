## 1. CDK App / Stack / Construct — три уровня абстракции

### Аналогия: строительство здания

```
┌──────────────────────────────────────────────────────────────────┐
│  CDK App = Строительная компания                                 │
│                                                                  │
│  Она управляет всем проектом. Знает про все здания.              │
│  Один файл: bin/app.ts  — точка входа, как main() в программе.  │
│                                                                  │
│  ┌────────────────────────────────────────────────────────────┐  │
│  │  Stack = Отдельное здание                                  │  │
│  │                                                            │  │
│  │  Каждое здание — отдельная единица развёртывания.          │  │
│  │  В CloudFormation = отдельный Stack.                       │  │
│  │  Можно деплоить/откатывать независимо.                     │  │
│  │                                                            │  │
│  │  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐     │  │
│  │  │  Construct   │  │  Construct   │  │  Construct   │     │  │
│  │  │              │  │              │  │              │     │  │
│  │  │  Кирпич,     │  │  Окно,       │  │  Дверь,      │     │  │
│  │  │  балка,      │  │  проводка,   │  │  замок —     │     │  │
│  │  │  плита —     │  │  труба —     │  │  любой       │     │  │
│  │  │  один ресурс │  │  один ресурс │  │  ресурс      │     │  │
│  │  └──────────────┘  └──────────────┘  └──────────────┘     │  │
│  └────────────────────────────────────────────────────────────┘  │
│                                                                  │
│  ┌────────────────────────────────────────────────────────────┐  │
│  │  Stack = Второе здание (другая команда)                    │  │
│  └────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────┘
```

### Соответствие CDK → CloudFormation → AWS

```
CDK код (TypeScript)       CDK synth          CloudFormation            AWS
─────────────────────  ──────────────►  ─────────────────────  ──────────────────
App                                     (несколько шаблонов)
  └── StorageStack                      StorageStack.template   → CF Stack
        └── Bucket("raw")               Resources:             → S3 Bucket
        └── Bucket("results")             RawBucket: ...        → S3 Bucket
  └── DatabaseStack                    DatabaseStack.template   → CF Stack
        └── Table("documents")           Resources:             → DynamoDB Table
```

### Правило одного стека

Один стек — одна зона ответственности. В реальных проектах принято разбивать так:

```
StorageStack   → S3 buckets
DatabaseStack  → DynamoDB tables
ApiStack       → API Gateway + Lambda
WorkflowStack  → Step Functions
MessagingStack → SQS + SNS
EcsStack       → ECS Cluster + Task Definitions
NetworkStack   → VPC, Subnets, Security Groups
```

Не кладите всё в один стек — при изменении одного ресурса CloudFormation пересматривает весь шаблон.

## 2. L1 vs L2 vs L3 конструкции CDK

### Аналогия: уровни готовности блюда

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  L1 — Сырые продукты (CloudFormation 1:1)                       │
│  ─────────────────────────────────────────────────────────────  │
│  Вы сами нарезаете, варите, солите.                             │
│  Полный контроль, максимум работы.                              │
│                                                                 │
│  Класс: CfnBucket, CfnTable, CfnFunction                        │
│  Префикс: Cfn (CloudFormation Native)                           │
│  Когда: когда L2 не поддерживает нужный параметр                │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  L2 — Полуфабрикат (Intent-based API)                           │
│  ─────────────────────────────────────────────────────────────  │
│  AWS уже подготовил заготовку с умными дефолтами.               │
│  Вы доводите до вкуса: добавляете шифрование, версионинг, CORS. │
│                                                                 │
│  Класс: Bucket, Table, Function, Queue                          │
│  Умные дефолты: encryption включена, versioning отключён, etc.  │
│  Методы: bucket.grantRead(fn), table.grantWriteData(fn)         │
│  Когда: 90% случаев — используйте L2                            │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  L3 — Готовое блюдо (Patterns)                                  │
│  ─────────────────────────────────────────────────────────────  │
│  Целый паттерн "из коробки": API + Lambda + DynamoDB за 5 строк │
│                                                                 │
│  Пакет: aws-solutions-constructs                                │
│  Пример: ApiGatewayToLambdaToDynamoDB                           │
│  Когда: типовые архитектурные паттерны, быстрый старт           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### Сравнительная таблица

```
┌──────────────────┬─────────────────┬────────────────────┬───────────────────┐
│                  │ L1 (Cfn*)        │ L2 (Bucket, etc.)  │ L3 (Patterns)     │
├──────────────────┼─────────────────┼────────────────────┼───────────────────┤
│ Уровень          │ CF 1:1          │ Высокоуровневый    │ Паттерн целиком   │
├──────────────────┼─────────────────┼────────────────────┼───────────────────┤
│ Сложность        │ Высокая         │ Средняя            │ Низкая            │
├──────────────────┼─────────────────┼────────────────────┼───────────────────┤
│ Гибкость         │ Максимальная    │ Высокая            │ Ограниченная      │
├──────────────────┼─────────────────┼────────────────────┼───────────────────┤
│ Умные дефолты    │ ❌ Нет           │ ✅ Есть            │ ✅ Есть           │
├──────────────────┼─────────────────┼────────────────────┼───────────────────┤
│ Grant методы     │ ❌ Нет           │ ✅ Есть            │ ✅ Есть           │
├──────────────────┼─────────────────┼────────────────────┼───────────────────┤
│ Типичное         │ Новый сервис    │ Большинство        │ MVP / прототип    │
│ применение       │ без L2          │ реальных проектов  │                   │
└──────────────────┴─────────────────┴────────────────────┴───────────────────┘
```

### Grant методы — почему это важно для Tech Lead

L2 конструкции имеют методы `grant*`, которые автоматически настраивают IAM политики по принципу Least Privilege:

```
Вместо того чтобы писать вручную политику:
  { Effect: Allow, Action: [s3:GetObject, s3:HeadObject], Resource: arn:... }

Вы пишете:
  rawBucket.grantRead(validateLambda)

CDK сам разберётся какие именно Action нужны для "читать из S3".
```

Это ключевой аргумент на собеседовании: CDK eliminates IAM policy boilerplate and enforces Least Privilege by default.

## 3. CDK languages — почему TypeScript

### Доступные языки

```
┌─────────────────┬──────────────────────────────────────────────────────┐
│ Язык            │ Статус                                               │
├─────────────────┼──────────────────────────────────────────────────────┤
│ TypeScript      │ ✅ Первый класс. CDK написан на нём. GA.             │
│ JavaScript      │ ✅ Поддерживается. Нет типов — не рекомендуется.     │
│ Python          │ ✅ Популярен среди Data/ML команд.                   │
│ Java            │ ✅ Поддерживается. Verbose.                          │
│ C#              │ ✅ Поддерживается.                                   │
│ Go              │ 🔶 Developer Preview.                               │
└─────────────────┴──────────────────────────────────────────────────────┘
```

### Почему TypeScript — правильный выбор для этого проекта

```
Причина 1: CDK написан на TypeScript
─────────────────────────────────────
Новые конструкты появляются в TypeScript первыми.
L2 для новых сервисов сначала выходят на TS, потом jsii генерирует биндинги.

Причина 2: Один язык на всём стеке
─────────────────────────────────────
  infrastructure/ → TypeScript CDK
  lambdas/        → TypeScript Lambda handlers
  tests/          → TypeScript Jest

= один tsconfig, один eslint, один набор знаний в команде.

Причина 3: Типизация CDK конструктов
─────────────────────────────────────
IDE подскажет какие параметры нужны для Bucket, Function, etc.
Опечатки в именах свойств = ошибка компиляции, не runtime ошибка.

Причина 4: jsii
─────────────────────────────────────
CDK использует jsii (JavaScript interoperability interface).
Код пишется на TypeScript → jsii автоматически генерирует биндинги для Python, Java, C#.
Поэтому всегда есть паритет между языками.
```

### Как CDK выполняется

```
                  CDK CLI
                     │
                     ▼
         node bin/app.ts (TypeScript)
                     │
                     ▼
         App.synth() — обходит дерево конструктов
                     │
                     ▼
         CloudFormation template (JSON/YAML)
                     │
                     ▼
         AWS CloudFormation API → реальные ресурсы
```

CDK — это не магия. Это TypeScript программа, которая при запуске строит дерево объектов, а потом сериализует его в JSON шаблон CloudFormation.

## 4. `cdk.json` — конфиг-файл CDK

### Что это и зачем

`cdk.json` — это манифест CDK проекта. Он говорит CDK CLI: "вот точка входа, вот флаги, вот настройки безопасности".

### Анатомия файла

```
{
  "app": "npx ts-node --prefer-ts-exts bin/app.ts",
  ──────────────────────────────────────────────────────────────
  ↑ Команда запуска. CDK не знает про TypeScript — он знает только
    как запустить произвольную команду и получить CF шаблон.
    npx ts-node — это TypeScript "на лету" без предварительного build.

  "context": {
    "aws-cdk:enableDiffNoFail": "true",
    ──────────────────────────────────────────────────────────────
    ↑ Context variables — key-value пары доступные в коде через
      app.node.getContext("key").
      Используются для: feature flags, environment-specific values,
      lookup cache (AZ, AMI IDs).

    "@aws-cdk/aws-ec2:defaultInstanceType": "t3.micro"
  },

  "watch": { ... },     ← cdk watch — hot reload для разработки
  "build": "npm run build"  ← pre-synth build step (если нужен)
}
```

### Feature flags в context

AWS CDK периодически меняет поведение конструктов, но не ломает старые проекты. Для этого используются feature flags в context:

```
"@aws-cdk/aws-s3:serverAccessLogsUseBucketPolicy": true
"@aws-cdk/aws-lambda:recognizeLayerVersion": true
```

При `cdk init` автоматически добавляются все актуальные feature flags для новых проектов. Это значит: новый проект использует современное поведение CDK "из коробки".

### Что НЕ надо хранить в cdk.json

```
❌ AWS Account ID (используйте env vars или CDK_DEFAULT_ACCOUNT)
❌ Secrets и пароли
❌ Access Keys
✅ Feature flags
✅ Environment-specific non-secret config (имена бакетов, регионы)
✅ Lookup cache (CDK записывает туда результаты AZ lookups)
```

## 5. `package.json` для CDK проекта

### Структура зависимостей CDK проекта

```
package.json в infrastructure/
─────────────────────────────────────────────────────────
dependencies:
  aws-cdk-lib          ← один мегапакет со ВСЕМИ конструктами CDK v2
                         (в CDK v1 нужно было ставить каждый сервис отдельно)
  constructs           ← базовые классы Construct, Stack, App
                         (версионируется отдельно от CDK)

devDependencies:
  aws-cdk              ← CDK CLI (cdk synth, cdk deploy, cdk diff)
                         В production это devDependency — нужен только для deploy
  typescript           ← компилятор
  ts-node              ← запуск TypeScript без предварительного build
  @types/node          ← типы для Node.js API
  jest / vitest        ← тесты
```

### CDK v1 vs CDK v2 — важный исторический факт

```
CDK v1 (до 2022):
  "dependencies": {
    "@aws-cdk/aws-s3": "^1.190.0",
    "@aws-cdk/aws-lambda": "^1.190.0",
    "@aws-cdk/aws-dynamodb": "^1.190.0",
    // ... по пакету на каждый сервис, версии должны совпадать
  }

CDK v2 (текущий):
  "dependencies": {
    "aws-cdk-lib": "^2.x.x"  // один пакет = все сервисы
  }
```

Для Tech Lead: CDK v2 — обязательно. v1 достиг EOL в июне 2023.

### Пример минимального package.json для CDK

```json
{
  "name": "infrastructure",
  "version": "0.1.0",
  "private": true,
  "scripts": {
    "build": "tsc",
    "synth": "cdk synth",
    "deploy": "cdk deploy --all",
    "diff": "cdk diff",
    "destroy": "cdk destroy --all"
  },
  "dependencies": {
    "aws-cdk-lib": "^2.x.x",
    "constructs": "^10.x.x"
  },
  "devDependencies": {
    "aws-cdk": "^2.x.x",
    "typescript": "~5.x.x",
    "ts-node": "^10.x.x",
    "@types/node": "^20.x.x"
  }
}
```

### Почему `constructs` — отдельный пакет

`constructs` — это низкоуровневая библиотека с базовыми классами (`Construct`, `Node`). Она используется не только CDK, но и другими инструментами (например, Terraform CDK, cdk8s для Kubernetes). Поэтому она версионируется независимо.

```
constructs ← базовый building block (не AWS-специфичный)
     ↑
aws-cdk-lib ← AWS-специфичные конструкты строятся поверх constructs
```

## 6. Жизненный цикл CDK: synth → diff → deploy

### Полная картина

```
Разработчик
    │
    │  cdk synth
    ▼
┌─────────────────────────────────────────────────────────┐
│  CDK Toolkit (локально)                                 │
│                                                         │
│  1. Выполняет bin/app.ts                                │
│  2. Строит дерево конструктов в памяти                  │
│  3. Вызывает app.synth()                                │
│  4. Сериализует в CloudFormation JSON                   │
│  5. Сохраняет в cdk.out/                               │
└─────────────────────────────────────────────────────────┘
    │
    │  cdk diff (опционально)
    ▼
┌─────────────────────────────────────────────────────────┐
│  Сравнение                                              │
│                                                         │
│  Загружает текущий CloudFormation stack из AWS          │
│  Сравнивает с новым шаблоном в cdk.out/                │
│  Показывает: что добавится, изменится, удалится         │
│                                                         │
│  ~ Modify: RawBucket (encryption: SSE-S3 → SSE-KMS)    │
│  + Add: ResultsBucket                                   │
│  - Remove: OldQueue                                     │
└─────────────────────────────────────────────────────────┘
    │
    │  cdk deploy
    ▼
┌─────────────────────────────────────────────────────────┐
│  CDK Deploy                                             │
│                                                         │
│  1. Загружает assets в S3 (Lambda zip, Docker images)  │
│  2. Вызывает CloudFormation CreateChangeSet             │
│  3. CloudFormation применяет изменения                  │
│  4. CDK ждёт завершения + показывает прогресс           │
│  5. Выводит Outputs (API URL, ARN, etc.)                │
└─────────────────────────────────────────────────────────┘
    │
    ▼
AWS ресурсы созданы / обновлены
```

### Команды и когда их использовать

```
┌────────────────────┬────────────────────────────────────────────────────────┐
│ Команда            │ Когда использовать                                     │
├────────────────────┼────────────────────────────────────────────────────────┤
│ cdk synth          │ Проверить что код компилируется в валидный CF шаблон.  │
│                    │ Без обращения к AWS. Быстро.                           │
├────────────────────┼────────────────────────────────────────────────────────┤
│ cdk diff           │ Перед деплоем. Проверить "а что изменится?".           │
│                    │ Обязательно в prod, рекомендуется в dev.               │
├────────────────────┼────────────────────────────────────────────────────────┤
│ cdk deploy         │ Задеплоить один стек: cdk deploy StorageStack          │
│ cdk deploy --all   │ Задеплоить все стеки.                                  │
├────────────────────┼────────────────────────────────────────────────────────┤
│ cdk destroy        │ Удалить ресурсы. Stateful ресурсы (S3, DynamoDB)       │
│                    │ по умолчанию защищены от удаления.                     │
├────────────────────┼────────────────────────────────────────────────────────┤
│ cdk bootstrap      │ Один раз на аккаунт+регион. Создаёт CDKToolkit stack   │
│                    │ с S3 bucket для assets и IAM roles для deploy.         │
├────────────────────┼────────────────────────────────────────────────────────┤
│ cdk watch          │ Dev режим: автоматический re-deploy при изменении кода. │
│                    │ Только для development окружения.                      │
└────────────────────┴────────────────────────────────────────────────────────┘
```

### cdk.out/ — что туда попадает

```
cdk.out/
├── StorageStack.template.json    ← CF шаблон
├── DatabaseStack.template.json
├── manifest.json                 ← метаданные: стеки, ассеты
├── tree.json                     ← дерево всех конструктов
└── asset.abc123.zip              ← Lambda код, упакованный для загрузки в S3
```

`cdk.out/` должен быть в `.gitignore` — это артефакты сборки, не исходники.

## 7. Типичные вопросы на интервью

**Q: Чем CDK отличается от CloudFormation и Terraform?**

> CloudFormation — это декларативный JSON/YAML который вы пишете вручную. CDK — это TypeScript программа которая генерирует CloudFormation. Terraform — отдельный инструмент с собственным state management (tfstate), не привязанный к CloudFormation. CDK даёт вам преимущества ООП (переиспользование, абстракции, типизация) поверх CloudFormation.

**Q: Что такое CDK Bootstrap и зачем он нужен?**

> Bootstrap создаёт вспомогательную инфраструктуру в вашем AWS аккаунте: S3 bucket для хранения Lambda ZIP архивов и Docker образов, IAM роли с правами на deploy. Без bootstrap CDK не знает куда загрузить assets перед созданием Lambda функций. Нужно запустить один раз на каждую комбинацию аккаунт + регион.

**Q: В чём разница между L1, L2, L3 конструктами?**

> L1 — 1:1 маппинг с CloudFormation ресурсом, полный контроль, нет умных дефолтов. L2 — высокоуровневые обёртки с умными дефолтами безопасности и grant методами для IAM. L3 — готовые архитектурные паттерны из нескольких сервисов. В production коде используем L2 как основной уровень, L1 только когда L2 не поддерживает нужный параметр.

**Q: Почему стоит разбивать инфраструктуру на несколько Stack, а не один?**

> Один большой стек — это единая точка отказа при деплое. Если обновление DynamoDB таблицы провалится, откатывается весь стек включая S3 и Lambda. Раздельные стеки: независимые циклы деплоя, понятная граница ответственности, параллельный деплой командами, проще читать `cdk diff` перед деплоем.

**Q: Как CDK обеспечивает Least Privilege для IAM?**

> Через grant методы L2 конструктов: `bucket.grantRead(fn)` автоматически создаёт IAM policy с минимальным набором Action необходимых именно для чтения из S3. Разработчик не пишет IAM JSON вручную — CDK знает какие именно разрешения нужны для каждой операции.

**Q: Что такое CDK Aspects и когда их использовать?**

> Aspects — это механизм "visit pattern" поверх дерева конструктов. Позволяет применить правило ко всем ресурсам определённого типа. Пример: добавить тег `Environment=prod` ко всем ресурсам стека, или проверить что все S3 buckets имеют encryption включённую (compliance). Используется для cross-cutting concerns которые не хочется дублировать в каждом конструкте.
