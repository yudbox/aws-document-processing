## 1. AWS Free Tier — что входит, лимиты

### Три типа Free Tier

AWS Free Tier — это не одна акция, а три разных механизма:

```
┌─────────────────────┬──────────────────────────────┬──────────────────────────────┐
│ Тип                 │ Как работает                 │ Пример                       │
├─────────────────────┼──────────────────────────────┼──────────────────────────────┤
│ Always Free         │ Бесплатно навсегда           │ Lambda: 1M req/мес           │
│                     │ для всех аккаунтов           │ DynamoDB: 25 GB storage      │
├─────────────────────┼──────────────────────────────┼──────────────────────────────┤
│ 12 Months Free      │ Первые 12 месяцев с момента  │ EC2 t2.micro: 750 часов/мес  │
│                     │ создания аккаунта            │ S3: 5 GB standard storage    │
├─────────────────────┼──────────────────────────────┼──────────────────────────────┤
│ Trials              │ Короткий триал при первом    │ SageMaker: 2 месяца          │
│                     │ использовании сервиса        │ Inspector: 90 дней           │
└─────────────────────┴──────────────────────────────┴──────────────────────────────┘
```

### Ключевые лимиты для нашего проекта

| Сервис          | Always Free лимит                       | Что будет при превышении    |
| --------------- | --------------------------------------- | --------------------------- |
| **Lambda**      | 1 000 000 запросов/мес + 400 000 GB-сек | ~$0.20 за следующий миллион |
| **DynamoDB**    | 25 GB хранилище + 25 RCU + 25 WCU       | ~$0.25 за GB/мес            |
| **API Gateway** | 1 000 000 HTTP API вызовов/мес (12 мес) | ~$1.00 за следующий миллион |
| **SQS**         | 1 000 000 запросов/мес                  | ~$0.40 за следующий миллион |
| **SNS**         | 1 000 000 публикаций/мес                | ~$0.50 за следующий миллион |
| **CloudWatch**  | 10 метрик, 10 алармов, 5 GB логов       | По прайсу выше лимита       |

### Аналогия для интервью

> Free Tier — это как кредитная карта с кредитным лимитом который вам никто не напоминает. Лимит тихо кончается, и вы начинаете платить. Поэтому billing alerts обязательны.

### Что важно знать как Tech Lead

- Free Tier не распространяется на **data transfer out** полностью — исходящий трафик за пределы AWS региона тарифицируется
- Лимиты считаются **на уровне аккаунта**, не на уровне пользователя
- Если организация использует AWS Organizations — каждый дочерний аккаунт имеет свои Free Tier лимиты

## 2. AWS Account vs IAM User vs IAM Role

### Аналогия: здание с системой доступа

```
┌─────────────────────────────────────────────────────────┐
│  AWS Account = Само здание (вся инфраструктура)         │
│                                                         │
│  ┌───────────────┐    ┌───────────────────────────┐     │
│  │  Root User    │    │  IAM Users                │     │
│  │               │    │                           │     │
│  │  Владелец     │    │  Сотрудники с именными    │     │
│  │  здания.      │    │  пропусками.              │     │
│  │  Ключи от     │    │  Каждый знает кто это     │     │
│  │  всего.       │    │  и что он делал.          │     │
│  │  Не трогать   │    │                           │     │
│  │  в будний     │    │  alice (developer)        │     │
│  │  день.        │    │  bob (devops)             │     │
│  └───────────────┘    └───────────────────────────┘     │
│                                                         │
│  ┌──────────────────────────────────────────────────┐   │
│  │  IAM Roles = Временные бейджи                    │   │
│  │                                                  │   │
│  │  "На этот объект" выдаётся временный бейдж       │   │
│  │  с конкретными правами доступа.                  │   │
│  │                                                  │   │
│  │  Lambda Function → получает роль "read S3"       │   │
│  │  ECS Task       → получает роль "write DynamoDB" │   │
│  │  Developer      → assume role "deploy-role"      │   │
│  └──────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

### Ключевые отличия

```
┌──────────────────┬────────────────────────────┬────────────────────────────────┐
│                  │ IAM User                   │ IAM Role                       │
├──────────────────┼────────────────────────────┼────────────────────────────────┤
│ Кто использует   │ Человек или приложение     │ AWS сервис, другой аккаунт,    │
│                  │ с постоянным доступом      │ федеративный пользователь      │
├──────────────────┼────────────────────────────┼────────────────────────────────┤
│ Учётные данные   │ Постоянные (Access Key +   │ Временные (до 12 часов),       │
│                  │ Secret Key)                │ автоматически ротируются       │
├──────────────────┼────────────────────────────┼────────────────────────────────┤
│ Привязка         │ К конкретному человеку     │ Ни к кому — любой может        │
│                  │                            │ assume если разрешено          │
├──────────────────┼────────────────────────────┼────────────────────────────────┤
│ Где применяется  │ CI/CD, локальная разработка│ Lambda, ECS, EC2, cross-account│
├──────────────────┼────────────────────────────┼────────────────────────────────┤
│ Best practice    │ Минимально необходимо,     │ Предпочтительный способ для    │
│                  │ всегда с MFA               │ всех сервисов AWS              │
└──────────────────┴────────────────────────────┴────────────────────────────────┘
```

### Root User — когда использовать

Root — это единственный аккаунт, который нельзя ограничить политиками. Он используется только для:

- Изменения плана поддержки
- Закрытия аккаунта
- Восстановления доступа когда все IAM User заблокированы
- Активации IAM access to Billing

**Правило:** Root user = ключи от сейфа в банке. Кладём под замок и не трогаем.

### Флоу assume role

```
┌──────────────┐     1. AssumeRole request      ┌──────────────────┐
│  Lambda Fn   │  ─────────────────────────────► │   AWS STS        │
│              │                                  │ (Security Token  │
│              │  ◄─────────────────────────────  │  Service)        │
│              │   2. Temporary credentials       └──────────────────┘
│              │      (AccessKey + SecretKey
│              │       + SessionToken, 1 час)
│              │
│              │     3. API call with temp creds  ┌──────────────────┐
│              │  ─────────────────────────────►  │   S3 / DynamoDB  │
└──────────────┘                                  └──────────────────┘
```

## 3. IAM политики: managed vs inline

### Аналогия: должностные инструкции

Представьте корпорацию:

- **Managed Policy** = стандартная должностная инструкция из HR. Написана один раз, применяется к любому сотруднику нужной должности. Если инструкция меняется — меняется у всех.
- **Inline Policy** = персональные поправки, прибитые гвоздями к конкретному сотруднику. Исчезают вместе с ним.

### Два вида Managed Policies

```
Managed Policies
├── AWS Managed (созданы Amazon)
│   ├── AdministratorAccess   ← "Всё разрешено"
│   ├── ReadOnlyAccess        ← "Только читать"
│   ├── AmazonS3FullAccess    ← "Полный доступ к S3"
│   └── ...400+ готовых политик
│
└── Customer Managed (созданы вами)
    ├── DocumentProcessorPolicy  ← ваши кастомные правила
    └── DeploymentPolicy
```

### Структура IAM политики

```json
{
  "Effect":    "Allow" | "Deny",
  "Action":    "s3:GetObject" | ["s3:*", "dynamodb:Query"],
  "Resource":  "arn:aws:s3:::my-bucket/*",
  "Condition": { "StringEquals": { "aws:RequestedRegion": "eu-central-1" } }
}
```

Аналогия для запоминания: **EARC** — Effect, Action, Resource, Condition.

### Когда что использовать

```
┌────────────────────┬─────────────────────────────┬──────────────────────────────┐
│                    │ Managed Policy               │ Inline Policy                │
├────────────────────┼─────────────────────────────┼──────────────────────────────┤
│ Переиспользование  │ ✅ Одна на много User/Role   │ ❌ Только для одного          │
├────────────────────┼─────────────────────────────┼──────────────────────────────┤
│ Управление         │ ✅ Обновляется централизованно│ ❌ Нужно обновлять вручную    │
├────────────────────┼─────────────────────────────┼──────────────────────────────┤
│ Жизненный цикл     │ ✅ Независимая сущность       │ ❌ Удаляется с хостом         │
├────────────────────┼─────────────────────────────┼──────────────────────────────┤
│ Когда применять    │ Стандартные роли в команде   │ Уникальные права, которые    │
│                    │ и сервисах                   │ не должны переиспользоваться │
└────────────────────┴─────────────────────────────┴──────────────────────────────┘
```

### Порядок вычисления (важно для интервью)

```
Запрос поступил
        │
        ▼
1. Есть явный Deny?  ──► ДА ──► ОТКАЗАТЬ (конец)
        │ НЕТ
        ▼
2. Есть явный Allow? ──► ДА ──► РАЗРЕШИТЬ (конец)
        │ НЕТ
        ▼
3. По умолчанию      ──────────► ОТКАЗАТЬ (implicit deny)
```

> **Правило:** В IAM всё запрещено по умолчанию. Allow должен быть явным. Deny всегда побеждает Allow.

## 4. AWS Access Keys vs Session Tokens

### Аналогия: ключи и временные пропуска

```
┌─────────────────────────────────────────────────────────┐
│                                                         │
│  Access Key + Secret Key                                │
│  = Ключ от квартиры                                     │
│                                                         │
│  • Постоянный                                           │
│  • Выдаётся IAM User-у                                  │
│  • Хранится в ~/.aws/credentials                        │
│  • Если утёк — нужно немедленно деактивировать          │
│  • Ротируется вручную (best practice: каждые 90 дней)   │
│                                                         │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│                                                         │
│  Session Token (Temporary Credentials)                  │
│  = Временный пропуск на конкретный объект               │
│                                                         │
│  • Временный (15 минут — 12 часов)                      │
│  • Выдаётся через AWS STS (AssumeRole)                  │
│  • Состоит из трёх частей:                              │
│    - AccessKeyId (временный)                            │
│    - SecretAccessKey (временный)                        │
│    - SessionToken (proof что это temp creds)            │
│  • Если утёк — автоматически протухнет                  │
│  • Используется Lambda, ECS, EC2, IAM Identity Center   │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### Где что хранится

```
Локальная разработка:
~/.aws/credentials
├── [default]
│   ├── aws_access_key_id = AKIA...         ← постоянный
│   └── aws_secret_access_key = xyz...      ← постоянный

Lambda / ECS / EC2:
Переменные окружения (автоматически)
├── AWS_ACCESS_KEY_ID      ← временный, ротируется автоматически
├── AWS_SECRET_ACCESS_KEY  ← временный
└── AWS_SESSION_TOKEN      ← proof of temp session
```

### Почему Session Tokens безопаснее

```
Сценарий: утечка credentials в GitHub

┌────────────────────┬───────────────────────────────────────────────┐
│                    │ Последствия                                   │
├────────────────────┼───────────────────────────────────────────────┤
│ Access Key утёк    │ Злоумышленник использует его вечно пока       │
│                    │ вы не деактивируете вручную.                  │
│                    │ Окно риска: часы/дни                          │
├────────────────────┼───────────────────────────────────────────────┤
│ Session Token утёк │ Автоматически протухает через N минут/часов.  │
│                    │ Окно риска: минуты                            │
└────────────────────┴───────────────────────────────────────────────┘
```

> **На интервью:** "В production мы никогда не используем долгосрочные Access Keys в сервисах. Lambda и ECS получают временные credentials через IAM Roles автоматически. Access Keys — только для CI/CD pipeline, с минимальными правами и ротацией."

## 5. MFA (Multi-Factor Authentication)

### Три фактора аутентификации

```
Что ты ЗНАЕШЬ        Что ты ИМЕЕШЬ       Что ты ЕСТЬ
(Knowledge)          (Possession)         (Inherence)
     │                     │                   │
  Пароль              Телефон с          Отпечаток
  PIN-код             TOTP-кодом         пальца
                      YubiKey            Face ID
```

MFA в AWS — комбинация **первых двух**: пароль + одноразовый код.

### Типы MFA устройств в AWS

```
┌───────────────────────┬────────────────────────────────────────────┐
│ Тип                   │ Описание                                   │
├───────────────────────┼────────────────────────────────────────────┤
│ Virtual MFA           │ Приложение на телефоне (Google Authenticator│
│ (TOTP-приложение)     │ Authy, 1Password). Генерирует 6-значный    │
│                       │ код каждые 30 секунд по алгоритму TOTP.    │
├───────────────────────┼────────────────────────────────────────────┤
│ Hardware TOTP token   │ Физический брелок (Gemalto). То же TOTP,   │
│                       │ но в железе. Для высокой безопасности.     │
├───────────────────────┼────────────────────────────────────────────┤
│ FIDO2 Security Key    │ YubiKey, Titan Key. USB/NFC ключ.          │
│ (U2F)                 │ Самый защищённый — phishing-resistant.     │
├───────────────────────┼────────────────────────────────────────────┤
│ SMS MFA               │ Код по SMS. Устаревший, уязвим к SIM-swap. │
│                       │ AWS не рекомендует для production.         │
└───────────────────────┴────────────────────────────────────────────┘
```

### Как TOTP работает (для понимания алгоритма)

```
Секретный ключ (shared secret)
         │
         │ + текущее время (30-секундный интервал)
         │
         ▼
     HMAC-SHA1
         │
         ▼
  6-значный код

AWS и ваш телефон знают один и тот же секрет →
генерируют одинаковый код в одно и то же время →
сравнивают → совпало = аутентификация прошла
```

### MFA для Root vs IAM Users

```
Root Account MFA                    IAM User MFA
─────────────────                   ────────────────
ОБЯЗАТЕЛЬНО всегда.                 Рекомендуется.
Без исключений.                     Можно сделать обязательным
                                    через политику:
                                    Condition: {
                                      "Bool": {
                                        "aws:MultiFactorAuthPresent": "true"
                                      }
                                    }
```

### Зачем MFA на Root особенно важен

Root нельзя ограничить ни одной IAM политикой. Если Root скомпрометирован — злоумышленник может:

- Создать новых Admin пользователей
- Удалить все ваши ресурсы
- Закрыть аккаунт
- Получить доступ к billing данным

MFA — единственный барьер, который это предотвращает.

## 6. AWS Billing Alerts

### Три инструмента мониторинга затрат

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  AWS Cost Management                                        │
│                                                             │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────────┐  │
│  │  AWS Budgets │  │  Cost Explorer│  │  CloudWatch      │  │
│  │              │  │              │  │  Billing Alarm   │  │
│  │  Проактивный │  │  Реактивный  │  │  Старый способ   │  │
│  │  алерт ДО    │  │  анализ ПОСЛЕ│  │  через метрику   │  │
│  │  превышения  │  │  трат        │  │  EstimatedCharges│  │
│  │              │  │              │  │                  │  │
│  │  Рекомендован│  │  Для анализа │  │  Работает только │  │
│  │  для всех    │  │  и оптимизации│  │  в us-east-1     │  │
│  └──────────────┘  └──────────────┘  └──────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

### AWS Budgets — типы бюджетов

```
Cost Budget     → алерт когда траты превышают $X
Usage Budget    → алерт когда использование превышает N единиц
                  (например, > 800 000 Lambda invocations)
Savings Plans   → мониторинг покрытия Reserved/Savings Plans
Reservation     → мониторинг утилизации Reserved Instances
```

### Как работает алерт на $10 (наш проект)

```
Создаём бюджет:
  Лимит: $10/месяц
  Алерты:
    85% ($8.50) → email "приближаемся к лимиту"
    100% ($10)  → email "лимит достигнут"
    forecasted 110% → email "прогноз превышения"
          │
          ▼
  AWS Budgets мониторит траты каждые ~8-12 часов
          │
          ▼
  При срабатывании → SNS Topic → Email / Slack / Lambda
```

### Почему нужно делать сразу

Реальный сценарий без алертов:

```
День 1:  Оставил EC2 t3.large включённым случайно
День 2:  Забыл про него
День 30: Получил счёт на $150
         Осознал что это было 730 часов × $0.208/ч
```

С алертом:

```
День 1:  Оставил EC2 включённым
День 2:  Получил email "вы потратили $5 из $10"
         Понял что что-то не так → остановил EC2
```

### Лучшие практики для Tech Lead

1. **Бюджет на каждый проект/команду** — не один общий, а отдельные для dev/staging/prod
2. **Алерт на forecasted cost** — предупреждает до факта, не после
3. **Cost allocation tags** — тегировать все ресурсы `Project=doc-processing, Env=dev` чтобы видеть разбивку
4. **AWS Cost Anomaly Detection** — автоматически находит аномалии (резкие спайки) через ML, без пороговых значений

### Быстрая шпаргалка для ответа на интервью

> "В нашем проекте мы настраиваем бюджет $10/мес через AWS Budgets сразу при создании аккаунта. Это страховка от случайных трат. Дополнительно включаем Cost Anomaly Detection — он замечает подозрительные паттерны, которые пороговые алерты пропустят: например, атаку с тысячами мелких запросов, каждый из которых ниже порога, но суммарно дорого."

## Итоговая схема безопасности аккаунта

```
AWS Account
    │
    ├── Root User
    │   ├── ✅ MFA включён (FIDO2 или TOTP)
    │   ├── ✅ Access Keys НЕ созданы (удалены если были)
    │   └── ✅ Используется только для исключительных задач
    │
    ├── IAM Users
    │   ├── serverless-lab (наш проект)
    │   │   ├── ✅ AdministratorAccess policy
    │   │   ├── ✅ MFA включён
    │   │   ├── ✅ Access Keys в ~/.aws/credentials
    │   │   └── ⚠️  НЕ в production, только для разработки
    │   └── ... другие пользователи
    │
    ├── IAM Roles (для сервисов)
    │   ├── LambdaExecutionRole → временные credentials
    │   ├── ECSTaskRole         → временные credentials
    │   └── CDKDeployRole       → временные credentials
    │
    └── AWS Budgets
        ├── Cost Budget $10/мес → email алерт
        └── Cost Anomaly Detection → ML-based алерт
```

## Типичные вопросы на интервью и ответы

**Q: Чем IAM Role отличается от IAM User?**

> User — это долгосрочная идентичность с постоянными credentials, привязанная к человеку или приложению. Role — это набор прав без привязки к конкретной сущности, выдаётся временно через STS. Для сервисов AWS (Lambda, ECS) всегда используем Role, никогда не прячем Access Keys в код.

**Q: Что такое принцип наименьших привилегий и как вы его применяете?**

> Каждая сущность получает ровно те права, которые нужны для выполнения своей задачи — не больше. В CDK это реализуется через `.grantRead()`, `.grantWrite()` вместо `*` в политиках. Lambda для чтения из S3 получает только `s3:GetObject` на конкретный bucket, не `s3:*`.

**Q: Если Access Key утёк в GitHub — что делаете?**

> Немедленно деактивируем ключ в IAM Console (не удаляем сразу — сначала деактивируем чтобы не нарушить работу). Создаём новый. Проверяем CloudTrail на предмет подозрительных API вызовов за последние часы. Если использовался злоумышленником — инцидент, уведомляем AWS Support. В будущем — git pre-commit hook с `git-secrets` для предотвращения.

**Q: Почему не стоит работать под Root?**

> Root нельзя ограничить IAM политиками. Любая ошибка или компрометация под Root — катастрофа. Правило: Root создаёт первого Admin IAM User, включает MFA на Root, и дальше всё делается через IAM Users и Roles.
